# Quests Module

The Quests module turns database-authored quest graphs into deterministic runtime quests. It owns quest selection, graph construction, requirements, actions, event processing, progress persistence contracts, loot construction, enemy fleet construction, and the public `IQuestManager` API.

The module lives in `Assets/Modules/Quests/` and compiles as the `Quests` assembly. Runtime types use the `Domain.Quests` namespace. Quest records and their generated visitor interfaces are owned by the [Database module](database.md); application state and side effects are supplied through context interfaces implemented under `Assets/Scripts/Domain/Quests/`.

## Runtime Flow

```text
Database QuestModel + session QuestProgress
                    |
                 QuestFactory
                    |
                 QuestBuilder
        +-----------+------------+
        |           |            |
    NodeBuilder  requirement   enemy/loot caches
        |          builders         |
        +-----------+---------------+
                    v
             Quest graph (INode)
                    |
 QuestEvent --> QuestManager.Tick --> automatic transitions
                    |
         action-required node --> IQuestActionProcessor
                    |
          new node/status --> IQuestDataStorage + UI signals
```

`Assets/Scripts/Installers/GameInstaller.cs` is the application composition root. It binds the context and provider implementations, `QuestFactory`, `RequirementsFactory`, and a non-lazy singleton `QuestManager`, then exposes quest-list, action-required, and quest-event signals.

The assembly references Zenject, CommonComponents, Database, Localization, Diagnostics, and Utilites. It intentionally does not depend on the combat, session, star-map UI, or economy assemblies.

## Quest Data and Construction

Quest content is authored as `QuestModel` data under `Assets/Modules/Database/Resources/Database/Quests/`. Generated database node and requirement variants dispatch to the hand-written factories in this module.

`QuestFactory` supports two construction paths:

- New quests start from a `QuestModel`, star ID, and deterministic seed generated by `IQuestDataProvider`.
- Restored quests start from persisted `QuestProgress`, which records quest ID, star ID, active node ID, and seed.

`QuestBuilder` creates per-quest enemy, loot, and requirement caches, then asks `NodeBuilder` to materialize the graph. Node references are resolved recursively and cached by ID, so loops in authored graphs do not create duplicate runtime nodes. If restored progress names a missing node, the builder falls back to the graph's lowest node ID.

`QuestInfo` carries resolved parameters such as the origin star and seed. Keep random choices derived from this quest seed or a documented event seed so saving and reloading cannot silently change a quest's generated content.

## Graph Execution

Every runtime node implements `INode`. The contract separates three kinds of progress:

- `TryProceed` performs immediate transitions that need no external event or user action.
- `TryProcessEvent` reacts to a typed `IQuestEventData` payload and returns the next node when matched.
- `TryInvokeAction` delegates an application side effect through `IQuestActionProcessor`.

When a quest enters a node, `Quest` initializes it and follows immediate transitions until it reaches a waiting node or terminal state. Both `Quest` and `QuestManager` cap transition processing at 100 iterations to detect accidental infinite graph loops.

Node families include:

- Dialog and branching: `TextNode`, `SwitchNode`, `ConditionNode`, and `RandomNode`.
- Encounters: `BattleNode` and `AttackEnemyNode` with separate victory and defeat transitions.
- UI actions: trading, shipyard, workshop, and retreat.
- Rewards and inventory: loot and item removal.
- World changes: faction and character relations, faction ownership, starbase capture/power, and occupant suppression.
- Quest composition: starting another quest.
- Terminal results: complete, fail, cancel, coming-soon, and undefined/error.

Action nodes do not directly load scenes or mutate application state. They call `IQuestActionProcessor`, which is implemented by the application layer and can open dialogs, start combat, trade, modify the galaxy, grant access to shipyard/workshop UI, or launch another quest.

## Requirements

Requirements implement both the quest-start and node-transition views through `IRequirements`, or one of the narrower `IQuestRequirements` and `INodeRequirements` contracts. `RequirementsBuilder` maps database requirement variants to runtime checks.

Available checks cover boolean composition, current/origin star properties, faction and hostility, reputation, character relations, inventory/artifacts, prior quest state, starbase ownership and power, occupant aggression, elapsed quest time, and time since completion. Requirements also supply localized explanatory text where a dialog or quest list needs it.

`RequirementCache`, `EnemyCache`, and `LootCache` ensure repeated references within one generated quest resolve consistently. Extend these caches when new content has randomized or parameterized construction that must be shared across several nodes.

## Start Conditions and Events

On session creation, `QuestManager` restores active progress and immediately starts database quests with the `GameStart` condition. It also partitions the remaining catalog into start-condition collections for beacon, local encounter, new-star, arrival, faction mission, and daily selection.

The manager consumes these event types:

- `ArrivedAtStarSystem`
- `NewStarSystemSecured`
- `ActionButtonPressed`
- `BeaconActivated`
- `LocalEncounter`
- `CombatCompleted`
- `OccupantsDefeated`
- `FactionMissionAccepted`
- `Timer`

Some events first select a new eligible quest from the matching collection, then every active quest gets a chance to process the event. A timer event is also generated after each ten seconds of total play time to advance time-based requirements and daily selection.

Quest eligibility depends on `QuestType`: temporary quests are unrestricted; common and urgent quests cannot duplicate the same quest/star pair; singleton quests cannot duplicate an active ID; storyline quests cannot restart after completion. Daily cooldown is derived from weight plus seeded jitter.

## Persistence and Application Integration

The module defines its dependencies as small provider interfaces:

- `IQuestDataProvider` reads history and creates seeds; `IQuestDataStorage` additionally writes progress and final state.
- `IStarMapDataProvider` and its star/region views expose only geography, faction, relations, visit, capture, and power data needed by requirements.
- `IGameDataProvider`, `IInventoryDataProvider`, and `ICharacterDataProvider` expose session timing, inventory quantities, and character attitude.
- `ILootItemFactory` converts database loot choices into application-owned items.
- `IQuestManagerEventProvider` bridges session lifecycle and quest events into the manager and publishes UI-facing update notifications.

`QuestManager` writes non-temporary progress whenever a quest is added or updated. On completion, failure, or cancellation it records the final status, removes the active quest, refreshes beacons, and notifies consumers. Temporary quests run through the graph but are not persisted.

## Adding Quest Content or Behavior

For content that uses existing node and requirement types:

1. Edit the quest JSON in the Database module.
2. Keep node IDs stable for released quests because saved `QuestProgress` points to the active node ID.
3. Validate every transition target, terminal path, start requirement, localized string, loot reference, and enemy reference.

For a new serialized node or requirement type:

1. Add the variant to the Database schema and regenerate Database code; do not hand-edit generated visitors or models.
2. Add the runtime implementation under `Nodes/` or `Requirements/`.
3. Add the corresponding visitor/factory method to `NodeBuilder` or `RequirementsBuilder`.
4. Extend the relevant context interface only when the information cannot be expressed through an existing provider.
5. Add application-side behavior to the `IQuestActionProcessor` implementation when the node causes a new external side effect.

## Validation Checklist

There is currently no co-located Quests test assembly, so exercise the affected graph through Unity and verify persistence explicitly.

1. Start the quest through every applicable start condition and confirm ineligible starts are rejected.
2. Traverse every branch, including unmet requirements, cancel/failure paths, and repeated events.
3. Save and reload on each action-required node; confirm the same node, seed, loot, enemies, and requirements are restored.
4. Confirm completion history, cooldowns, quest beacons, and quest-list/action-required signals update once.
5. Verify graph loops settle before the 100-transition guard.
6. Test localized requirement and dialog text with missing and valid localization keys.
